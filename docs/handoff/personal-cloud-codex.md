# 个人云端交接说明

更新日期：2026-10-10  
读者：项目负责人本人，以及云算力服务器上的新 Codex 会话。

## 1. 先读什么

克隆仓库后按以下顺序阅读，读完即可接手：

1. 本文：确认目标、权限边界、当前真实进度和接手方式；
2. [云端协作说明](cloud-collaboration.md)：配置环境、取得资产、创建分支并交付 PR；
3. [当前状态](../status.md)：查看已经完成的实验和最近验证；
4. [实施方案](../plans/implementation-plan.md)：理解音频、视频两条算法路线；
5. [任务入口](issues/README.md)：领取已发布的音频、视频或数据 Issue；
6. [资产清单](local-assets.json)：查看旧机资产快照和服务器核对记录，再确认任务所需路径。

旧照片项目、暂停检查点和历史实验快照只用于追溯。它们不能覆盖本文和当前状态，也不能作为
新任务的默认入口。

## 2. 我的协作方式

代码已迁入云算力服务器，共享 cu132 开发环境已配置。接手时从现有工作副本和
[当前状态](../status.md) 开始，不再要求从旧电脑重新传代码。训练资产仍需按任务接入，
历史 Git bundle 和状态包仅作为可选恢复来源。标准协作流程是：

1. 我从 `docs/handoff/issues/` 选择或整理任务，在远端仓库发布 Issue；
2. 队友或云端 Codex 在独立分支完成实现、实验和必要文档，并提交 PR；
3. 我审查代码、实验依据、资源边界和复现信息；
4. 修改完成后，由我决定并执行合并。

云端执行者不要替我合并，不要把本地分支直接推到受保护分支。远端写权限、云账号、付费预算
以当次授权为准；当前已核实算力为 RTX 4090 24 GiB，其他未确认资源不要猜测。

## 3. 已确认的目标和工作偏好

- 同时完成音频和视频 AIGC 伪造识别，主指标为 EER，EER 越低越好；内部约定
  `real=0`、`fake=1`，高分表示更可能伪造。
- 用户已经报名，官方没有提供额外信息。不要再次索要比赛规范；平台样例出现后再修改适配层。
- 已确认的实施方案可以直接执行，不需要重新请求方案审批。
- 主线优先级是：可用数据、有效训练、EER、跨域泛化、双分支离线交付。
- 避免过度防御性编程、重复校验、重复证明和为假想异常扩建基础设施。一次入口校验后直接传递
  已解析对象；每轮实验保存一份必要记录即可。
- 小样本或单数据集结果用于选择下一步，需要明确局限，但不为此阻塞后续实验。
- Git 提交遵循 LoRA：Logical、Observable、Reversible、Atomic。一个提交完成一个明确目标，附与
  该目标相称的验证或实验证据，并可独立回退。
- 数据许可、已知组关系、dev/holdout 隔离、逐样本连续分数和失败记账属于必要边界。

## 5. Git 里有什么，缺什么

Git 跟踪代码、配置、文档、11项项目 skills 和小型实验摘要。项目skills随克隆可用；
不依赖原电脑的Codex会话、机器级skills或OMX运行态，普通Issue流程无需恢复那些状态。以下目录默认被忽略，克隆仓库后不会
自动出现：

- `data/`：训练、开发和派生清单；
- `models/`：HuBERT、ResNet18 等本地权重；
- `outputs/`：checkpoint、逐样本分数、缓存和训练日志；
- `cache/`、`external/`：可重建缓存和固定上游参考。

当前工作副本尚未接入训练所需数据、清单和权重；服务器 `/srv/shared-data` 已有 ASVspoof
parquet、ViF Panda/FakeSound ZIP 等产物，仍需核对协议并解码或导入，详情见协作说明。
先检查真实完成状态并复用。`local-assets.json` 包含旧机快照和2026-10-10服务器核对记录，
不是实时清单。按 `cloud-collaboration.md` 接入必要资产并核对来源和哈希；不要重复下载，
也不要把大数据、权重或训练输出直接提交进 Git。

## 6. 给云端 Codex 的首次交接 Prompt

下面内容可以在服务器仓库根目录直接发送给新的 Codex：

```text
你正在接手 AIGC 音视频伪造识别比赛项目。先完整阅读 AGENTS.md、
docs/handoff/personal-cloud-codex.md、docs/handoff/cloud-collaboration.md、
docs/status.md、docs/plans/implementation-plan.md，以及我指定的 Issue。

只执行该 Issue 的范围。先核对当前分支、仓库状态、云端 GPU/环境和
该任务需要的资产；local-assets.json 含旧机快照和有日期的服务器核对，不是实时清单。检查 /srv/shared-data
既有下载与产物，避免重复任务；不要假设 data/models/outputs 已随 Git 克隆。
使用 scripts/devctl run python -m deepfake_detection_archive 和 scripts/devctl check；
共享环境不安装具体 checkout 的项目。按现有 uv.lock 和项目入口工作，优先获得可比较的训练、EER 与泛化结果，避免重复校验、
过度防御性编程和新建平行框架。音频和视频都在项目范围内；用户已报名且官方没有额外资料，
不要再次索要赛题信息。

在独立分支提交 LoRA 风格的小而完整提交。实验必须说明数据划分、配置、种子、最佳 dev EER、
耗时/显存、失败数、checkpoint 与逐样本分数位置，并明确哪些结论尚未得到证明。运行与改动
相称的检查，提交前运行项目统一检查。完成后创建供我审查的 PR；不要自行合并，也不要声称
远端 CI、比赛成绩或未知生成器泛化，除非有对应证据。
```

发送 Prompt 时，再附上 Issue 链接、目标分支、已分配的云端规格和资产取得方式。未提供的
账号、预算或远端权限仍由我决定，Codex 应先完成不依赖这些信息的仓库内工作。

## 7. 我审查 PR 时看什么

- Issue 的验收条件是否逐项满足，改动是否保持单一目标；
- 数据划分、标签方向、EER 和逐样本失败是否正确，holdout 是否保持隔离；
- 比较是否只改变计划中的主要因素，是否把 profile、同域 dev 或元数据捷径夸成泛化成绩；
- 代码、数据和权重许可是否分别记录，大资产是否留在 Git 之外；
- 复现信息能否定位到配置、代码提交、资产版本、checkpoint、分数和简洁摘要；
- 针对性检查与统一检查是否有新鲜结果，远端 CI 状态是否按实际报告；
- 提交是否符合 LoRA，PR 是否可以安全回退且没有夹带无关整理。

合并后再从下一份 Issue 继续，不在同一个 PR 中顺手扩张到新的模型路线。
